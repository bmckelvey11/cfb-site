<objective>
Enrich the upcoming games produced by Plan 05-01 through the same feature path historical games use, so that any saved system — including one filtering on season-to-date stats — evaluates correctly against them (D-05).

This is not optional polish. `compute_running_stats` only produces useful values when the season's already-completed games are in the same input list. `games.csv` stops at 2025 and carries no rows for the current season, so a naive implementation gives every upcoming game zero games played and null season-to-date values. Null feature values fail closed, so every system with a season-to-date filter would silently match nothing — exactly the failure D-05 was written to prevent, and one that produces no error anywhere.

Purpose: a system that matches hundreds of historical games but zero upcoming games in week 8 looks like a broken feature, not a fail-closed convention.
Output: a running-stats union step and a features sidecar for upcoming games, written to their own path.
</objective>

  <action>
**Running stats over the union (D-05).** Plan 05-01 already fetches the full resolved season rather than only the target week's slice, precisely so the accumulation base is available here. Split those rows on the completed flag, then call `compute_running_stats` over the UNION of the season's completed games and the target-week games, with start dates populated from the raw kickoff values so the ordering is correct. Passing only the target week's games is the failure mode this task exists to prevent.

The entering-game guarantee is already structural and must be preserved, not re-implemented: the snapshot for each game is written before that game's result is folded in, and games with a null score are skipped during accumulation. So an unplayed game takes the accumulated state of all strictly prior games and contributes nothing to any other game's state, and several unplayed games in the same list cannot contaminate each other. Do not add any special-casing for unplayed games — the existing function is already correct for them.

Emit feature rows for the TARGET-WEEK game ids only. The completed games of the current season are accumulation input, not output.

**The sidecar (do not clobber the historical one).** `enrich_games` already accepts an explicit games list, so reuse it with the upcoming records. Its companion writer, however, targets a FIXED path — reusing it would overwrite the historical features sidecar. Add a sibling writer that takes an explicit output path, keeping the same envelope with a meta block and a games map so the existing reader works unchanged. Write the upcoming features to their own file under the processed directory.

Wire this into the upcoming build so a single run of the CLI command produces the games file, the meta file, and the features sidecar together.

**Expected coverage, and why it is acceptable.** The fields that reliably resolve for an unplayed game are the matchup features and the betting-line features, both sourced from the raw games and lines payloads that Plan 05-01 already writes. Post-game and near-game sourced features resolve to null, and the per-season advanced-stat and predicted-points source files are not fetched by this command, so those season-to-date fields resolve null too. Null fails closed, which is the established convention — do not add fallbacks, defaults, or placeholder values to make more filters fire. A loosely matched bet is worse than an unmatched one.
