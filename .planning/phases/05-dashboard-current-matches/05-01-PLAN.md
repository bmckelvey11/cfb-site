<objective>
Build the upcoming-games data path: a new `upcoming` CLI command that resolves the current CFB week (or falls back backward to the most recent completed week), fetches games and lines from CFBD, normalizes them through the existing join, and persists a separate processed file carrying kickoff time.

This is the data foundation for Current Matches (DASH-03). It implements D-01 (separate file, `games.csv` untouched), D-02 (CLI produces it, never a Flask request), D-03 (current week only), D-04 (no line means no row), D-06 (fetch timestamp recorded), D-07 and D-20 (offseason fallback resolves backward to the most recent completed week), and D-19 (postseason in scope, `season_type` threaded rather than hardcoded).

Purpose: without this file, Current Matches has nothing to render, and the phase is being built in an offseason where the fallback path is the only path that will be exercised live.
Output: `cfb_system_maker/upcoming.py`, upcoming save/load functions in `storage.py`, an `upcoming` CLI subcommand, and network-free tests.
</objective>

  <behavior>
    - `resolve_target_week(now, *, cfbd_module=None, token=None)` returns a resolution describing season, week, season_type, and is_fallback.
    - `build_upcoming(data_dir, *, now=None, cfbd_module=None, token=None)` returns records, kickoffs, and meta, and persists them.
    - Both are pure with respect to the injected client — no network when `cfbd_module` is supplied.

  <action>
Create `cfb_system_maker/upcoming.py`.

Follow the injectable-client seam from `scrapers.scrape`: accept `cfbd_module: Any = None` and resolve it as `cfbd_module or _load_cfbd_module()`. Import `_load_cfbd_module`, `_to_dict`, and `find_cfbd_token` from `cfbd_client` — do not copy them, and do not refactor `fetch_games_and_lines` (it constructs its own client and is deliberately left alone per RESEARCH §6).

**Week resolution (D-03, D-07, D-19, D-20).** Call `games_api.get_calendar(year)` for the season derived from `now`. Each returned week carries `season`, `week`, `seasonType`, `startDate`, `endDate`, all timezone-aware. Resolution order:
1. If a calendar window contains `now`, that is the target week. Carry its `seasonType` through to the games and lines calls — do not hardcode regular season (D-19). Postseason weeks are numbered on their own scale, so always pair week with season type; never compare week numbers across season types.
2. Otherwise resolve BACKWARD per D-20: find the most recent week that has completed games. Fetch that season's games and group the rows where `completed` is true by `(seasonType, week)`, choosing the group with the latest maximum `startDate`.
3. If the season derived from `now` has zero completed games — the real state today, because the 2026 season has not begun — step to the prior season and repeat step 2 there. Resolution must terminate: try at most two seasons back, then return a resolution with no target and let the caller write an empty-but-valid output.
Set `is_fallback` true for any resolution reached via steps 2 or 3.

**Fetching and normalizing.** For the resolved season, fetch the FULL season for BOTH games and lines — `get_games(year=season, season_type=...)` and `get_lines(year=season, season_type=...)`, neither filtered to the target week.

Full-season LINES are not an optimization; they are a correctness requirement. `normalize_games` drops any game whose line selection yields nothing, so a target-week-only lines fetch would leave the season's already-completed games unnormalizable. Plan 05-04 builds its running-stats accumulation base from those completed games, and without them every entering-game season-to-date value comes back null — the exact silent no-match D-05 exists to prevent. Fetching both in full here also avoids a second network pass in 05-04.

Normalize the TARGET WEEK's games against the full line set to produce the upcoming records.

Convert models with `_to_dict`, then pass the target week's game rows and the line rows to `normalize.normalize_games` unchanged. `_select_line` already owns provider precedence and the cross-provider total fallback, and its returning `None` for a game with no usable line IS the D-04 exclusion — implement no new exclusion logic.

**Kickoff join.** `normalize_games` emits `GameRecord`, which carries no date field. Build a separate mapping from the raw game payload keyed by game id, capturing `startDate` and `startTimeTBD`, and join it back to the normalized records by `game_id`. Use `normalize._first` semantics for key spellings if the raw rows vary in casing.

**Persistence.** Add to `storage.py`, mirroring `save_processed_games` / `load_processed_games`:
- `save_upcoming_games(data_dir, rows)` writing `data/processed/upcoming.csv`. Column order is the `GameRecord` field order followed by two trailing columns for kickoff and the TBD flag. This file is explicitly NOT bound by the `games.csv` field-order contract, and `games.csv` must not be read or written anywhere in this plan (D-01).
- `load_upcoming_games(data_dir)` returning parsed records plus kickoff data, reusing the existing `_none_if_blank` / `_optional_int` / `_optional_float` blank-to-None conventions — unplayed rows have empty score columns and must parse back to `None`, not to `0` or `""`.
- `save_upcoming_meta(data_dir, meta)` / `load_upcoming_meta(data_dir)` writing `data/processed/upcoming_meta.json` with `fetched_at`, `season`, `week`, `season_type`, `is_fallback`, `row_count`.

Serialize every datetime with `json.dumps(..., default=str)` exactly as `save_raw_json` does — a raw `startDate` is a `datetime` object after `_to_dict` and will raise `TypeError` otherwise.

Also write the raw payloads via the existing `save_raw_json(data_dir, "games", season, rows)` and `save_raw_json(data_dir, "lines", season, rows)`. Both dumps carry the FULL season, not the target week's slice. These files serve two consumers in Plan 05-04: `enrich._build_indexes` resolves matchup and betting-line features from them, and the running-stats accumulation base is rebuilt from them on disk. Persisting only the target week would leave 05-04 with no way to reconstruct the season's completed games, since the two plans run in separate executions and share nothing but the filesystem.

Never print, log, or persist the API token — pass it only into `Configuration`.
