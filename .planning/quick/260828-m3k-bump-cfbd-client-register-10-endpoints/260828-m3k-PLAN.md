# Quick Task: bump vendored `cfbd-python`, register the 10 blocked endpoints

`docs/data-coverage.md` names this as the deliberate separate change: the registry ceiling
is the vendored client, 11 commits behind upstream `main`, and the 10 unregistered spec
paths are exactly what landed in those commits.

Measured before planning:

- `cfbd-python/` is a **nested clone whose files the parent repo tracks as plain blobs**
  (524 files, mode 100644, no gitlink). So the bump is `git checkout` inside the nested
  repo, then commit the resulting 495-file diff in the parent.
- Upstream diff: **495 files, +13250/-2047**, one new API module (`playoffs_api.py`),
  145 models modified, ~30 added. Not a narrow additive bump — `e21965f openapi v3 spec
  compatibility`, `99d1208 coaches enrichment` and `dd354d5 fcs coverage expansion` all
  touch models the existing pipeline reads.

**Verify command:** `python -m pytest` plus a live key-signature diff (below).

## The regression risk the test suite can't see

`tests/test_scrapers.py` drives a **fake** cfbd module and `tests/test_cli.py` uses bundled
sample data, so a green suite says nothing about whether the real client still produces the
field spellings `normalize`/`enrich` index on. `normalize._first` tolerates multiple
spellings, but only ones already in its key list.

So the bump is bracketed by a live probe: for the 16 endpoints `build`/`enrich` consume,
call the real API and record the first row's (nested) key set. Captured pre-bump already
(`keys_before.json`, all 16 returned rows). Re-run post-bump and diff. Any key that
disappears is a break in a consumer path; any key added is inert.

## Tasks

1. Bump `cfbd-python` to upstream `main`, commit the vendored diff in the parent repo.
2. Re-run the live probe → diff key sets vs baseline. Removed keys get traced to their
   consumer in `normalize.py`/`enrich.py` and fixed, or reported as a blocker.
3. `python -m pytest` green (557 passed, 1 skipped before the bump).
4. Register the 10 endpoints in `scrapers.ENDPOINTS` with the mode each method's signature
   actually supports — modes come from `inspect.signature`, not from guessing, and each new
   endpoint gets one live call to confirm the mode/kwargs before it is registered.
5. `python scripts/audit_endpoints.py` → partition closes at **73 registered + 1
   client-only (`/info/usage`) + 0 no-client = 74**, drift bucket empty.
6. Update `docs/data-coverage.md`: the "blocked on a client bump" section becomes history.

## Done when

Audit shows 73/1/0, full suite green, and no key that a consumer indexes has vanished from
the live payloads. If a payload key did vanish, that is a finding to report and fix, not a
reason to keep the bump unshipped.
