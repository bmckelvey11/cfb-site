## The thing that would have gone wrong quietly

Postseason is week 1 in most seasons — but **2020 has week 20, 2023 has weeks 11-15, and
2025 has weeks 13-14**, the Division II/III playoff rounds that start in mid-November.
A hardcoded `week=1` pass would have dropped 32 games in 2025 alone and reported success.
`_postseason_weeks` reads the week list off the `games_{season}.json` seed instead, so it
cannot miss a week nobody thought to check. My own probe only sampled four seasons and saw
`{1, 13, 14}`; the seed found week 15 and week 20 as well.

This only became possible because `260828-j8s` put postseason rows into the games seed.
The two tasks compose.

## Verification

Row counts prove nothing here. `verify_postseason_split.py` (in this directory) checks
that for every `(endpoint, season, week)` the row sets in `_wk{w}.json` and
`_post_wk{w}.json` are **disjoint** — whole-row identity, stronger than any id field and
needing no per-endpoint schema — and that for `game_team_stats` 2024 wk1 their union equals
the live `season_type="both"` result: 137 + 50 = 187 ids, exact.

The old guard test asserted `both` stays `regular`, which this change makes false. Rewritten
rather than deleted: the invariant it protected — the two types never land in the same file
— still holds and is now asserted directly, plus a second test that the postseason week list
comes from the seed. Mutating the filename prefix to force a collision fails both.

## audit_coverage.py now expects the postseason files

Without that, a missing postseason pull is invisible — the same blindness that hid the
original `seasonType` gap. It reports five expected-but-absent files per endpoint:
`(2020, 20)`, `(2023, 11)`, `(2023, 12)`, `(2025, 13)`, `(2025, 14)`. All five are
**upstream empties, not misses** — probed live, they return 0 rows, while the neighbouring
`(2023, 13)` returns 8 team-stat rows and 1,120 plays. Same floor-not-failure shape the doc
already records for the empty `[]` payloads.
