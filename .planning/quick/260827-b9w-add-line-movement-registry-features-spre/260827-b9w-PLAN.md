# Quick Task: line-movement registry features (`spread_open`, `spread_move`, `total_open`, `total_move`)

Source: `docs/betting-system-builder-implementation-plan.md` Phase A, steps 1-2 (step 3
`spread_move_band` is explicitly optional/skip; step 4 is the enrich rerun, folded into
Task 2 here).

New registry features computed from data already on disk. **No `GameRecord`/CSV change** —
values land in the `features.json` sidecar via `enrich`.

**Verify command:** `.venv/Scripts/python.exe -m pytest`

---

## Findings that shape this plan (measured, not assumed)

Two things were measured against the real repo data before planning. Both change what the
plan says; read them before implementing.

### 1. The task brief's sign gloss is inverted — formula kept, prose fixed

The brief (and the constraints handed to the planner) said *"spread_move = close − open,
positive = moved toward home team."* The formula is right; the parenthetical is backwards.

`GameRecord.spread` is the **home** spread, negative favors home. So:

| open | close | `close − open` | what actually happened |
|------|-------|----------------|------------------------|
| -3 | -7 | **−4** | home became a bigger favorite → moved **toward home** |
| +7 | +9.5 | **+2.5** | home became a bigger underdog → moved **toward away** |

Real 2024 rows confirm the second case (UL Monroe home, Bovada open 7 → close 9.5).

**Decision: keep `spread_move = close − open`** (pinned by the source doc, line 53) and fix
the prose everywhere it appears. The About-panel description must say
**negative = moved toward the home team; positive = moved toward the away team.**
Surfacing rather than silently flipping the formula, per repo `CLAUDE.md` §1.

`total_move = close − open` needs no correction: positive = total went up.

### 2. Coverage is thin and starts in 2021 — this is correct, not a bug

The CFBD lines feed only carries `spreadOpen`/`overUnderOpen` for a few books:

| provider | lines | with `spreadOpen` |
|---|---|---|
| Bovada | 4,984 | 84% |
| DraftKings | 2,424 | 92% |
| ESPN Bet | 3,446 | 48% |
| **consensus** | **8,183** | **0%** |
| teamrankings / numberfire / William Hill / Caesars | 12,000+ | 0% |

`consensus` is the selected close row for 8,183 of 13,014 built games (every game before
2021). Because the same-book rule forbids reading an open off a *different* provider's row,
those games get `None`. Expected post-enrich coverage (simulated against `games.csv` +
`data/raw/lines_*.json`):

| season | games | `spread_open` | `total_open` |
|---|---|---|---|
| 2013-2020 | 6,301 | 0 (0%) | 0 (0%) |
| 2021 | 849 | 7 (1%) | 7 (1%) |
| 2022 | 1,413 | 17 (1%) | 17 (1%) |
| 2023 | 1,347 | 659 (49%) | 605 (45%) |
| 2024 | 1,507 | 772 (51%) | 342 (23%) |
| 2025 | 1,597 | 862 (54%) | 408 (26%) |
| **total** | **13,014** | **2,317 (17.8%)** | **1,379 (10.6%)** |

**Rejected alternative — do not "fix" this later by falling back to another provider's
open.** An open from Bovada minus a close from consensus is a cross-book basis difference,
not line movement. Fewer honest rows beats more fake ones. The descriptions must tell the
user why the book-matched feature is populated less often than the legacy `spreadOpen`.

### 3. Registering these silently puts them in the automated search space

`search.py:42` derives its candidate pool **by exclusion**:

```python
_CANDIDATE_FEATURES = tuple(f for f in FEATURE_REGISTRY if f.group != "result_lookahead")
```

So every new numeric non-lookahead feature is auto-included, and `_feature_children`
(`search.py:281`) will start emitting `spread_move >= X` / `<= X` candidates the moment
these four are registered. Nobody decided that.

It matters because a `spread_move` filter implicitly restricts the pool to the ~18% of
games where the feature is non-null — and that slice is not random, it is
"games a DraftKings/Bovada/ESPN Bet close was selected for, 2023-2025." A search finalist
found on it is a 2,300-game, three-season subsample reported through the same Wilson CI /
permutation p / BH pipeline as a 13,014-game backtest.

**Decision: exclude the four from automated search for now; keep them fully available for
manual system building** (which is what Phase A's "Done when" actually asks for). Quarantine
via `result_lookahead` would be a lie — these are genuine pregame values, and the group
triggers the UI's "lookahead — analysis only" warning. Use a narrow, named exclusion
instead (Task 1, step 6). Reversible: delete a key from one frozenset to opt in once
coverage improves.

> **Open decision for the developer:** if you would rather let the search try them now and
> lean on the existing low-sample gates, say so and drop Task 1 step 6 — the rest of the
> plan is unchanged.

## Design decisions

- **Re-selection is exact, verified.** `_select_line(lines, game.provider)` reproduces the
  close row for **13,014/13,014 games, 0 spread mismatches**. Passing `game.provider` (the
  provider normalize actually recorded) as the preference works whether the build-time
  `--provider` flag matched or fell back to `usable[0]`, so `enrich` does not need to know
  the build-time flag. Reuse `_select_total(lines, selected)` for the total so `total_open`
  pairs to the row that supplied `game.total` — which may be a different book than the
  spread's. Internally consistent per number; the description must not over-claim that the
  total open shares the spread's book.
- **New source kind `computed_line_move`**, keyed by `game_id`, built in `enrich.py`
  alongside `computed_running`. `team_scoped=False`, `join="game_id"`, so `_apply_feature`
  takes the plain `row[feature.key] = _lookup(...)` path — no team-scoped branches touched.
- **Do NOT touch `_index_raw_lines`.** It flattens to `lines[0]` and feeds the legacy
  `spreadOpen` / `overUnderOpen` / `moneylineHome` / `moneylineAway` features. Add a
  separate index; leave the old one alone.
- **Group is `betting_lines`, not "Line Info."** No `line_info` group exists. Reusing
  `betting_lines` avoids editing the three duplicated group lists (`features.py` `Group`
  Literal, `web.py` `_feature_options` ordering tuple, `test_features.py` allowed set).
- **Legacy duplicates stay.** Existing `spreadOpen` / `overUnderOpen` remain registered —
  removing them would break saved systems that reference the keys. New features get
  distinct labels so the sidebar is unambiguous.
- **Move is computed off `game.spread` / `game.total`** (the authoritative built close), not
  the raw row's — they are the same row by construction, and this keeps the sidecar
  consistent with the CSV.
- **Missing open → all four `None`** (fail closed). No zero defaults. If `spread_open` is
  `None`, `spread_move` is `None`; totals independently.

## Steps

### Task 1 — enrich source + registry defs + tests (one unit)

`enrich_games` iterates `FEATURE_REGISTRY`, so a value only reaches the sidecar if the
feature is registered. Source and registry defs cannot be split across tasks — the tests
would not pass.

**Files:** `cfb_system_maker/enrich.py`, `cfb_system_maker/features.py`,
`cfb_system_maker/search.py`, `tests/test_enrich.py`, `tests/test_search.py`

`tests/test_features.py` needs **no** change — it has no hardcoded `source_kind` allow-set
(its `source_kind` assertions at lines 53/77 are scoped to specific feature keys), and
`len(FEATURE_REGISTRY) >= 20` is a floor. The generic registry tests (`unique keys`,
`non-empty descriptions`, `valid groups`) will cover the four new entries automatically.

1. `features.py`: add `"computed_line_move"` to the `SourceKind` Literal.
2. `enrich.py`: add `_build_line_move_index(data_dir, seasons, games) -> dict[int, dict[str, float | None]]`.
   Import `_select_line`, `_select_total`, `_first` from `cfb_system_maker.normalize`. Per
   season, load `data/raw/lines_{season}.json` once into `{game_id: lines_list}` (skip if
   the file is absent). Per game: `selected = _select_line(lines, game.provider)`; if
   `None`, skip the game. Read `spread_open = selected.get("spreadOpen")`;
   `total_row = _select_total(lines, selected)`;
   `total_open = _first(total_row, "overUnderOpen", "over_under_open")`. Emit
   `{"spread_open", "spread_move", "total_open", "total_move"}` where
   `spread_move = game.spread - spread_open` only when both are non-`None` (else `None`),
   and `total_move = game.total - total_open` likewise. Coerce opens through a numeric guard
   the way `_coerce_numeric` does — a string or bool open must read `None`, not crash.
3. `enrich.py`: register `indexes["computed_line_move"] = _build_line_move_index(...)` in
   `_build_indexes` next to `computed_running`, and add the `_lookup` branch:
   `if feature.source_kind == "computed_line_move": return indexes["computed_line_move"].get(game.game_id, {}).get(feature.field)`.
4. `features.py`: four `FeatureDef`s in the `betting_lines` group, `join="game_id"`,
   `control="numeric"`, `team_scoped=False`, `source_kind="computed_line_move"`, `field`
   equal to the key. Keys and labels:
   - `spread_open` — "Spread Open (book-matched)"
   - `spread_move` — "Spread Move (close − open)"
   - `total_open` — "Total Open (book-matched)"
   - `total_move` — "Total Move (close − open)"

   Each `description` (required — `test_features.py` asserts non-empty) must state, in
   plain About-panel prose:
   - home-perspective sign, matching `GameRecord.spread` (negative favors home);
   - for the move features: **`close − open`; negative = the line moved toward the home
     team, positive = toward the away team** (totals: positive = total went up);
   - that the open is read from the **same book row as the close**, so it is null whenever
     that book publishes no opener — which is why it is populated on far fewer games than
     the legacy "Spread Open" feature, and on no games before 2021;
   - for `total_open` / `total_move`: the total's row may be a different book than the
     spread's, per existing `_select_total` behavior.
5. `search.py`: keep the four out of the automated candidate pool (finding 3). Add a named
   frozenset next to `_CANDIDATE_FEATURES` — e.g.
   `_LOW_COVERAGE_KEYS = frozenset({"spread_open", "spread_move", "total_open", "total_move"})`
   — with a short comment giving the reason (non-random ~18% / 2023-2025 subsample, not a
   quality judgement on the feature), and subtract it in the existing comprehension:
   `if f.group != "result_lookahead" and f.key not in _LOW_COVERAGE_KEYS`. Add one test to
   `tests/test_search.py` asserting no candidate produced by `expand_candidates` carries a
   `spread_move` (or sibling) `FeatureFilter`, so re-enabling later is a deliberate act that
   trips a test rather than a silent drift.
6. Tests in `tests/test_enrich.py`, following the existing fixture pattern (write raw JSON
   into `tmp_path / "raw"`, construct `GameRecord`s, call `enrich_games(tmp_path, games)`):
   - **`test_line_move_reads_open_from_the_close_providers_row`** — one game, two provider
     rows; the row matching `GameRecord.provider` carries the open, the other carries a
     *different* open. Assert `spread_open` is the matched row's value, not the other's.
     Use a home-favorite-lengthening fixture (open `-3.0`, close `-7.0`) so
     `spread_move == -4.0` and the sign is load-bearing, not ambiguous. Assert `total_open`
     / `total_move` on the same row too.
   - **`test_line_move_none_when_the_close_providers_row_has_no_open`** — two provider rows
     where the *non-selected* provider has the open and the selected one does not. All four
     features `None`. This is the cross-book guard; it is the case that actually happens in
     production data (consensus close, Bovada open).
   - **`test_line_move_none_when_no_open_values_present`** — single provider, no
     `spreadOpen`/`overUnderOpen` keys at all → all four `None`.

**Verify:**
`.venv/Scripts/python.exe -m pytest tests/test_enrich.py tests/test_features.py tests/test_search.py`
then the full `.venv/Scripts/python.exe -m pytest`.

**Done when:** the three new enrich tests and the search-exclusion test pass, the full suite
is green, and no existing `spreadOpen`/`overUnderOpen` test or behavior changed.

### Task 2 — rerun enrich and confirm coverage against the measured baseline

`registry_version()` hashes sorted registry keys, so adding four keys bumps it and the web
UI will show the stale-sidecar warning until `enrich` reruns.

**Files:** `data/processed/features.json` (regenerated; not hand-edited)

1. `.venv/Scripts/python.exe -m cfb_system_maker enrich --data-dir data`
2. Count non-null `spread_open` and `total_open` in the regenerated sidecar, per season.
3. Compare against the measured baseline in the findings table above.

**Verify (falsifiable):** the regenerated sidecar has **~2,317** games with non-null
`spread_open` and **~1,379** with non-null `total_open`; **0** in every season 2013-2020;
roughly 49% / 51% / 54% in 2023 / 2024 / 2025. A material divergence from these numbers
means the source is selecting the wrong row — investigate, do not accept.

**Done when:** counts match the baseline, the stale-sidecar warning is gone, and the four
features appear under Betting Lines in the sidebar with a working numeric filter modal
(`/filter-detail` is registry-generic — no endpoint change expected; if the modal needs
code, that is a finding to report, not to fix in this task).
