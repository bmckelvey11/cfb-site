## Fix 3 — cumulative chart emits one circle per bet (13,003 circles)

**Files:** `cfb_system_maker/web.py`, `tests/test_web.py`

**Action:**
`_cumulative_chart()` (~line 1546) builds one point per bet with no downsampling; the
template renders a `<circle>` + `<title>` per point (`index.html` ~517-521) — ~26k DOM
nodes on an unfiltered backtest.

Chosen approach: **keep the polyline at full fidelity, thin only the circles.**
Justification: the polyline is the signal and is a *single* DOM node regardless of point
count, so full fidelity there is free in node terms and guarantees zero visible distortion
of the equity curve; the circles were the entire explosion (2 nodes each). Capping the
whole point list instead would stride-skip local drawdowns and visibly alter the curve,
which the review explicitly forbids.

This needs **no template change** — `index.html` already reads `cumulative_chart.polyline`
(line 516) and `cumulative_chart.points` (517) as separate values.

- Compute the **full** point list first, exactly as today (x scaling divides by
  `len(ordered) - 1`). Do not thin `running_values` before computing x — that silently
  rescales the whole chart.
- Build `polyline` from the full point list (unchanged).
- Return `points` as a stride sample of the full list capped at `_CHART_POINTS_CAP` (60,
  already defined at web.py:80), always retaining the final point so the ending equity
  value stays hoverable. Mirror the existing stride idiom in `_range_chart` (~1513-1519).
- `min_x`/`max_x` stay `0` / `len(ordered) - 1` — already independent of `points`, so the
  `Bet N` axis labels keep meaning the true first/last bet index.
- Each retained point keeps its true `order`, so the `<title>` still reads the real bet
  number and its running total.

Do not violate two existing tests:
- `test_cumulative_chart_empty_bet_details_returns_zero_line_only` asserts **exact dict
  equality** — do not add a new key (no `circle_points`); reuse `points`/`polyline`.
- `test_cumulative_chart_single_bet_keeps_raw_stake_units` asserts
  `set(point.keys()) == {"x","y","order","profit"}` — thinned points keep exactly those four.

Out of scope: pixel-level polyline coordinate dedupe. One DOM node is already ~10x fewer
bytes than today's 13k circle+title pairs; further compression is not worth the code.

**Verify:** `.venv/Scripts/python.exe -m pytest tests/test_web.py -k cumulative`

**Done:** New test with >60 bets asserts `len(points) <= 60`, polyline coordinate-pair
count equals the bet count, last point's `order == n-1`, and `max_x == n-1`. It also
asserts the first retained point's `x == 28` and the last retained point's `x == 492`
(`width - pad_x`) — this is what pins x-scaling to the *full* list; thinning before
scaling bunches the points leftward and fails only this assertion. The three existing
multi-bet cumulative tests (≤3 bets) still pass untouched.

## Fix 1 — Feature Filters sidebar has ~90 flat launchers, no search, no collapse

**Files:** `cfb_system_maker/templates/index.html`, `cfb_system_maker/static/feature_sidebar.js` (new),
`cfb_system_maker/static/styles.css`, `tests/test_filter_modal.py`

**Action:**
The Feature Filters section (`index.html` ~161-337) renders every feature as a full-width
`.filter-launcher` inside a `<fieldset class="feature-group">`. Season To Date alone is 24
buttons. Add (a) a live substring search and (b) per-group collapse with an active-count
badge.

New file `static/feature_sidebar.js` (not appended to `filter_modal.js`) so Fixes 1 and 2
do not both edit the same file and can be committed independently. Add a second
`<script src=... defer>` beside the existing one at `index.html:615`. This is safe:
`test_web.py:1096 test_dashboard_loads_no_javascript` asserts `"<script" not in html` for
`/` (dashboard.html), not `/system` (index.html) — confirmed.

Decisions the executor must not re-litigate:
- **Search input is added to the template** with `class="filter-search"`, hidden by default
  and shown via a class the new script adds to `<html>` (do not depend on the `js` class
  `filter_modal.js` sets — guard independently). Mirrors the existing
  `.filter-launcher` / `.js .filter-launcher` progressive-enhancement pattern.
- **The input must have NO `name` attribute.** It sits inside `filters-form`, so a named
  input would be serialized into every backtest query and saved system.
- **Enter inside the input must `preventDefault()`** — otherwise it submits the form.
- **Hide non-matching rows with `display:none` only — never `disabled`.** `display:none`
  inputs still serialize, which is required: searching must not drop already-committed
  filters from the form.
- **Groups start expanded.** Search, not collapse, is what solves "scroll to find Wind
  Speed"; collapsing by default would change the most visible thing on the page.
  localStorage persistence is out of scope.
- **Search overrides collapse.** While a term is active, groups holding matches must show
  their matching rows even if collapsed; groups with zero matches hide entirely, legend
  included, so the user does not scroll past 8 empty legends.
- **Badge counts once at page load** — `fieldset.querySelectorAll('input[name="ff_enable"]:checked').length`.
  Modal Save calls `filtersForm.requestSubmit()` → full page reload, so no MutationObserver
  and no live recount. Render `0` as no badge.
- **Scope to the Feature Filters section only** — do not touch the core `.filter-group`
  launchers (Season/Week/Team/etc.).
- **Must not depend on Fix 2 landing first.** Match the search term against the launcher
  text *within each `.filter-launch-row`*, so a row holding two buttons (pre-Fix-2) still
  matches on either label.
- Matching is case-insensitive substring against the button label.

a11y: `aria-label` on the search input; collapse toggle is a `<button>` with `aria-expanded`
inside the `<legend>`; badge is a `<span>` carrying an accessible "N active" label.

CSS: add `.filter-search` (hidden-by-default + shown-when-enhanced pair) and a
`.feature-group.is-collapsed` rule hiding `.filter-launch-row`, beside the existing
`.feature-group` rules (~610-635) and the progressive-enhancement block (~740-765).

**Verify:** `.venv/Scripts/python.exe -m pytest tests/test_filter_modal.py tests/test_web.py`

**Done:** Render-level test asserts the search input is present on `/system` **and carries
no `name` attribute**; JS source-contract test (same `Path(...).read_text()` grep pattern
as the existing modal contract tests, e.g. `test_filter_modal.py:203-234`) asserts
`feature_sidebar.js` uses `style.display`/a hide class and never sets `.disabled`, calls
`preventDefault` on Enter, and counts `ff_enable` checked inputs for the badge. Full suite
green. No-JS path unchanged (`.filter-fallback` `<details>` blocks still render and submit).

## Fix 2 — every team-scoped feature renders two launchers (Bet-side + Opponent)

**Files:** `cfb_system_maker/templates/index.html`, `cfb_system_maker/static/filter_modal.js`,
`tests/test_filter_modal.py`

**Action:**
`index.html` ~197-223 emits two `.filter-launcher` buttons per team-scoped feature when
`form.bet_type == "spread"`, doubling the sidebar. The modal already has a working
perspective toggle — `renderPerspectiveControl()` (filter_modal.js:794) is called from both
`renderValueTable()` (:929) and `renderNumericControls()` (:1325), each passing
`() => reloadFeatureDetail()`, with options built from `state.allowedPerspectives`. So the
in-modal switching UI needs no work. Collapse to one launcher and fix the state-read path.

**The real defect this closes is a silent wrong write, not just stale display:** open a
feature with committed bet-side bounds 10-20, switch to Opponent (which has nothing
committed), press Save → `writeNumericToForm` (:1561) writes the still-in-`state` 10-20
into the **opponent** rows. `reloadFeatureDetail()` refreshes rows/domain/perspective but
never re-reads `state.min`/`state.max`, so the bet-side bounds survive the switch.

1. **Template:** drop the second (`— Opponent`) button block and the `— Bet-side` label
   suffix, leaving one launcher per feature. Stop emitting `data-perspective` on that
   launcher so `committedNumericBounds(candidateId, null)` picks whichever perspective is
   actually constrained and `resolveInitialPerspective` (:102) returns it, falling back to
   `defaultPerspective()` (:69 — `bet_side` for spread, `either` for totals).
2. **filter_modal.js:** in `reloadFeatureDetail()`'s numeric branch, after the domain
   refresh and before `renderNumericControls()`, re-resolve
   `committedNumericBounds(state.candidateId, state.perspective)` and reset
   `state.min`/`state.max` — mirroring the open path's fallback at :1774-1779 (a finite
   committed bound wins, otherwise the refreshed domain edge). This location is already
   precisely scoped to "perspective changed": `reloadFeatureDetail` has exactly two call
   sites and both are the `renderPerspectiveControl` onChange. `state.singleValuePick` is
   already reset at :893, so domain-edge clearing stays correct after a switch.

Do not touch (guardrails against over-deletion):
- Keep the `data-perspective` branch inside `resolveInitialPerspective` — the results-page
  "active filters" Edit chips still pass it. Only stop *emitting* the attribute on the
  sidebar launcher.
- Keep **both** hidden bound-pairs in the `.filter-fallback` (index.html 239-276) and the
  `dual` / `primary_p` / `secondary_p` Jinja machinery that fills them. That markup is the
  form-serialization contract; only the two `<button>` blocks collapse to one.
- Keep the per-perspective `[data-bound-perspective]` read (:308-343) and write (:1594-1625)
  logic as-is — one chip still edits exactly one perspective's rows per Save.
- Categorical team-scoped features are also affected (the launcher block wraps every
  `team_scoped` feature regardless of control). No extra work: their fallback renders a
  *single* `<select name="ff_perspective">` (296-310), so the two launchers were already
  overwriting each other there; one launcher is strictly closer to the form contract, and
  `writeFeatureToForm` already writes `state.perspective` into that select (:1556-1558).
- Categorical `state.selected` surviving a perspective switch is pre-existing behavior of
  the already-shipped toggle — out of scope.
- The results-page per-perspective Edit chips (`sentences`) keep rendering separately —
  they are genuinely distinct active filters.

Accepted loss, documented rather than discovered later: the sidebar button no longer reads
"— Bet-side"/"— Opponent" and launchers carry no active-state marker, so the sidebar stops
showing *which* side is constrained. That information still renders in the results-page
active-filters sentences. Do not add an active marker.

**Verify:** `.venv/Scripts/python.exe -m pytest tests/test_filter_modal.py tests/test_web.py`

**Done:** Render test asserts a team-scoped feature emits exactly one `.filter-launcher`
and that `— Opponent` no longer appears in the sidebar, while both
`data-bound-perspective="bet_side"` and `data-bound-perspective="opponent"` hidden rows
still render. JS source-contract test asserts `reloadFeatureDetail`'s body calls
`committedNumericBounds` and reassigns `state.min`/`state.max`. Full suite green.
