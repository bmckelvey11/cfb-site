<objective>
Ship three bundled example systems so an empty install has something that visibly works, on their own Example Systems tab.

This delivers DASH-02 and implements D-14 (checked-in JSON in the package, loaded read-only, never copied into the user's data directory on first run), D-15 (separate tab, never mixed into My Systems), D-16 (one example per capability — a spread system, a total system, and one exercising a registry feature), D-17 (each carries a written theory), and D-21 (the registry-feature example uses a matchup or line-derived feature, never a season-to-date stat).

D-21 is the constraint that makes this work rather than merely load. Season-to-date fields are null for the current season until games are played, and the advanced-stat source files this phase never fetches leave them null regardless. A season-to-date example would render zero matches during exactly the offseason-and-early-season window this ships in — the worst possible first impression for a bundled example. Examples exist to demonstrate the tool's range and to model writing down a hypothesis, not to present profitable angles as recommendations.

Purpose: an example that loads fine but matches zero games fails DASH-02.
Output: three JSON files in the package, an examples enumerator and loader, the Example Systems tab, and a Copy to My Systems action.
</objective>

**The three files (D-16).** Create a directory for examples inside the package and author one file per capability: a spread system, a total system, and one exercising a registry feature. The package is never installed — it runs from the repo root — so locate the directory relative to the module file. Do not reach for a package-resources API; it would be complexity with no payoff here.

Each file must match the exact JSON shape the existing system serializer produces: top-level name, saved timestamp, theory, and a nested system object. The parser defaults every field so a partial file would load, but write full files anyway so they diff cleanly against real saved systems. The most reliable way to author them correctly is to build each in the editor, save it, and copy the resulting file into the package directory.

Filename stems must satisfy the existing safe-name pattern — lowercase words joined by hyphens, no spaces and no dots — because those stems flow through the loader and through the copy action's save path.

**Content constraints, all load-bearing:**
- No provider filter on any example. The historical consensus provider no longer appears in recent data, and upcoming rows carry real sportsbook names, so a provider filter would match zero upcoming games while looking like a bug.
- No weather feature on any example. Weather is near-game data that will not exist for an unplayed game.
- The registry-feature example uses a matchup or betting-line feature, never a season-to-date stat (D-21). Matchup features and line features populate for any unplayed game with a posted line.

**Theory text (D-17).** One or two sentences per example on why the angle might exist. Write them as hypotheses, not claims — the point is modelling the habit of recording reasoning before trusting a backtest, and the tab note already states these are not betting recommendations.

**Loader.** Add an enumerator and a loader to `storage.py` shaped like the existing saved-system pair but rooted at the package examples directory instead of a data directory. Reuse the existing safe-name gate and the existing system-from-dict parser — do not write a parallel parser, and do not bypass the name gate. The existing saved-system functions are bound to a data directory and cannot see the package directory, which is why this sibling exists.

**Tab and table.** Add the scope tab strip with the two known values to `dashboard.html`, defaulting to My Systems and falling back to the default for any unrecognized value. The Example Systems tab reuses the same table shape and columns as My Systems, with three differences: a muted note above the table stating these are bundled examples demonstrating what the tool can filter on and are not betting recommendations; each row expanding its theory as wrapped body text in a subdued block beneath the system name; and a per-row secondary Copy to My Systems action.

Figures for example rows come from the same backtest path and the same cache the My Systems table uses. Do not add a second figure path for examples.

**Copy action.** Copy to My Systems loads the bundled example and saves it through the existing save path into the user's data directory, then returns the user to the Example Systems tab. Route the destination name through the existing safe-name gate — this is a user-reachable filesystem write and is exactly where a traversal-shaped name must be rejected. The bundled file is never written to, never deleted, and never modified in place (D-14).

Rely on Jinja's automatic escaping for example names and theory text; do not disable escaping on any of them. Add no new hex color values and no JavaScript.
