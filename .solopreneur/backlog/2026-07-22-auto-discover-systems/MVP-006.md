## Description
Standalone verification pass proving the NFRs empirically against representative data: search completes in minutes not hours, no full `run_backtest` occurs during beam expansion, and results are reproducible. The "Final gate" from the spec's Verification Plan — kept separate from unit tests since it needs representative-scale data and elapsed-time/call-count instrumentation, not just fixture-scale correctness checks.

## Acceptance Criteria
- [ ] Benchmark test/script runs `search` (or `search.py`'s internals directly) against representative data volume (~13k games scale, or the largest available built dataset) and records: candidate count, finalist count, elapsed wall time, peak beam size.
- [ ] Benchmark confirms **no full `run_backtest` call occurs during beam expansion** — call-count instrumentation/spy, not just a timing inference.
- [ ] Recorded elapsed time is within "minutes, not hours" — target-minute runtime documented as a comment/assertion threshold. Flag to CEO if representative-data run exceeds ~10 minutes as a sign the two-tier design isn't holding.
- [ ] `.venv\Scripts\python.exe -m pytest -q` passes in full (all prior MVP tickets' tests included) as the final gate.
- [ ] Reproducibility: seeded RNG confirmed for any randomized component search touches (permutation test inside the one `run_backtest` per finalist already uses `seed=42` default in existing `_permutation_p_value` — confirm this default is preserved/not overridden with an unseeded call anywhere in the search path).

## Technical Notes
- Likely a new test file (e.g. `tests/test_search_benchmark.py`) or a benchmark script under `scripts/`. "Final gate" language suggests it should be runnable as part of the same verification pass; recommend pytest with a `@pytest.mark.slow`-style opt-in if the suite needs to stay fast by default — check `pytest.ini` before introducing a new marker convention; don't silently make the default `pytest` invocation take minutes.
- Needs actual built data (`data/processed/games.csv` + `features.json`) at realistic scale to be meaningful — point the benchmark at the CEO's existing local `data/` dir (already built, per project docs: "13k games, enriched with running-stats features") rather than shipping 13k rows of fixture data into the repo.
- This ticket is explicitly where the "flagged risk" (hour-plus runtime) gets proven false — if the benchmark reveals it's NOT false, that's a finding to surface, not silently patch around, since it would mean MVP-003's beam mechanics need redesign.

## Finding (accepted 2026-07-30)
Default search params (`beam_width=100`, `max_dimensions=4`, `min_decided_bets=100`) do
NOT meet the spec's original "minutes, not hours" target at real ~11.4k-game scale:
`beam_search()` alone measured 25.8 min (50,390 candidates, peak beam hit the full 100
cap by round 2); full flow with `grade_finalists` measured 21.2 min. CEO decision:
accept the measured runtime rather than narrow search defaults or the benchmark's
scope — `MAX_ELAPSED_SECONDS` in the benchmark reflects this ceiling with headroom,
not the original aspirational target. Root cause documented in the benchmark's module
docstring: round 1's dominant survivors (e.g. `pregame_win_prob >= 0.977`) each
re-expand into ~280 children per round across 4 rounds, compounding to 50k+ evals —
not a bug, beam search exhausting a wide grammar (49 candidate features) at scale.
