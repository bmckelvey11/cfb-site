## Description
New module `search.py`. Implements the core+registry-feature candidate space: what a "candidate" is, how it's uniquely identified, which predicate combinations are legal, and how candidate values (including numeric quantile bins) are derived from **in-sample data only**. Pure, side-effect-free candidate generator — no evaluation, no beam logic yet.

## Acceptance Criteria
- [x] Candidate identity uses canonical sorted serialization of all `SystemFilter` and `FeatureFilter` fields — used for both deduplication and tie-breaking in later ranking.
- [x] `SystemFilter`'s `set`-typed fields (`seasons`, `weeks`, `teams`, `conferences`, `providers`) are **sorted explicitly** before iteration — never relies on Python's randomized set-iteration order.
- [x] Candidate grammar adds exactly one compatible predicate per dimension per expansion step:
  - [x] Never combines mutually exclusive choices in one candidate (`favorite`+`underdog`, `home`+`away`, incompatible spread/total predicate pairs).
  - [x] Never duplicates a dimension already set in the parent candidate.
  - [x] Never emits an unchanged/default-only candidate (the empty/no-op `SystemFilter`).
- [x] `result_lookahead`-tagged registry features are excluded from candidate generation entirely — never appear as a candidate predicate, at generation time, not filtered post hoc.
- [x] Numeric feature filters use a **fixed quantile scheme (e.g. quartiles)** to generate candidate threshold values — MVP does not attempt smarter binning.
- [x] Boolean and categorical feature values are derived from **in-sample feature rows only**, sorted, and capped per dimension at a documented deterministic limit (e.g. top-N most frequent categorical levels, explicitly stated in code/docstring).
- [x] Missing feature values (`None`/absent) never become a candidate value.
- [x] Quantile/value derivation takes an explicit in-sample game list/feature map as input — function signature makes it structurally impossible to pass holdout rows in.
- [x] Filter-dimension cap (default 4, hard cap 6 — configurable) is enforced at generation/expansion time, counting **dimensions** (e.g. "spread threshold" = 1 dimension), not values — explicitly distinct from `count_overfit_filters`'s value-counting, untouched by this ticket.
- [x] Team-scoped feature candidate generation defaults to `bet_side` perspective only for MVP (confirmed scope-narrowing decision — see backlog.md cross-cutting risk #5). Document this choice in a docstring/comment.
- [x] `tests/test_search.py` (new file): deterministic enumeration/ordering (same input → same candidate list, same order, twice); incompatible-predicate exclusion; lookahead-feature exclusion; in-sample-only value/quantile derivation (holdout rows passed in a test double never influence output); canonical dedup (two differently-ordered but semantically identical filter sets collapse to one identity).

## Technical Notes
- New file: `cfb_system_maker/search.py`.
- New file: `tests/test_search.py`.
- Reuses `SystemFilter`, `FeatureFilter` from `models.py` as-is — no schema change here.
- Reads `FEATURE_REGISTRY`/`FEATURE_BY_KEY` from `features.py` to enumerate candidate feature dimensions; filter by `group != "result_lookahead"`.
- Quantile computation needs the in-sample `feature_map` (from `enrich.load_features`) joined against in-sample `GameRecord`s — accept both as plain arguments, don't reach into `storage`/`enrich` itself (keep `search.py` pure, matching `backtest.py`'s pattern of taking games/feature_map as params).
- Canonical serialization: likely a tuple-of-sorted-tuples representation of the frozen dataclass fields — since `SystemFilter`/`FeatureFilter` are already frozen dataclasses, a deterministic `repr`-like key function is enough; no hashing needed beyond dict/set-membership dedup.
